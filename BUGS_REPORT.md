## Виправлено у цій і попередній сесіях
1. Адмінка: виправлено блокування додавання товару через приховане `required` поле PSU.
2. Адмінка: додано завантаження фото товару прямо з сайту (файл + URL).
3. API товарів: додано endpoint `POST /api/products/upload-image`.
4. Сервер: додано роздачу статичних файлів з `photos/`.
5. Замовлення: виправлено падіння `Unknown column 'customer_address'` через сумісність зі старою схемою:
 - `ALTER TABLE orders ADD COLUMN customer_address TEXT` у `setupDatabase`
 - runtime-перевірка схеми в `orderModel` перед створенням замовлення
6. Checkout (сервер): додано валідацію `customer_phone` (10-15 цифр), `total_price > 0`, структури `items` (валідні `product_id`/`quantity`).
7. Реєстрація: додано політику складності пароля на сервері і синхронізовано з клієнтом.
8. Адмінка: прибрано повторне навішування однакових `change`-listeners для полів характеристик.
9. Профіль користувача: опціональні `phone` і `default_address` уже реалізовані (реєстрація, профіль, автопідстановка в checkout).

## Відкриті задачі

### 1) Непослідовний формат API-відповідей
**Серйозність:** Середня  
**Де:** `server/controllers/*`  
**Проблема:** Частина контролерів повертає `{ success, data, message }`, частина має інші варіації.  
**Що потрібно:** уніфікувати контракт відповідей по всьому API.

### 2) Слабка цілісність `orders` ↔ `products`
**Серйозність:** Середня  
**Де:** `orders.items` як JSON, без FK  
**Проблема:** можливі "висячі" позиції в історичних замовленнях після видалення товарів.  
**Що потрібно:** або `order_items` з FK, або soft-delete товарів + заборона фізичного delete при зв'язаних замовленнях.

### 3) Немає повноцінної системи міграцій БД
**Серйозність:** Низька/Середня  
**Проблема:** схема оновлюється точковими `ALTER` у коді.  
**Що потрібно:** інструмент міграцій (`knex`, `db-migrate`, `sequelize-cli` тощо).

### 4) Немає backup-стратегії
**Серйозність:** Низька  
**Проблема:** немає регламенту/скриптів резервного копіювання.  
**Що потрібно:** додати backup/restore процес і задокументувати.

### 5) Немає версіонування API
**Серйозність:** Низька  
**Проблема:** роутинг без префікса версії (`/api/v1`).  
**Що потрібно:** запровадити версію API для безпечних змін контрактів.

### 6) Жорсткий fallback timeout у клієнті
**Серйозність:** Низька  
**Де:** `client/js/app.js`  
**Проблема:** fallback-таймаут 10s може бути замалим для повільних мереж/сервера.  
**Що потрібно:** централізувати конфіг таймаутів і зробити оверрайд через env/config.

### 7) Відсутні автоматичні тести/CI для критичних сценаріїв
**Серйозність:** Середня  
**Проблема:** регресії (типу `customer_address`, checkout, admin add product) виявляються вже після ручного тестування.  
**Що потрібно:** мінімум smoke/integration тести для auth, products, orders.

## Що не вдалося закрити зараз
1. Повна уніфікація API-контрактів (потребує ширшого рефакторингу всіх контролерів).
2. Перехід на нормалізовану схему замовлень (`order_items`) без плану міграції даних.
3. Інфраструктурні задачі (міграції, backup, CI) потребують окремого технічного етапу.
